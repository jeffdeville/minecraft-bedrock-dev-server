# Teaching Bedrock add-on development: sources, API facts, lesson sequence

Research report, 2026-09-06. Feeds the
[project plan](../2026-09-06-guided-course-plan.md). Audience: a ~12-year-old
who knows Minecraft deeply and has never programmed.

Context that shapes everything below: this repo's loop (`mc dev` → rsync → `install-packs.py` → activate → restart) replaces every tutorial's "copy into `development_behavior_packs` and activate in the world settings" step. The learner just saves into the watched folder. Every "activate the pack" instruction in the sources maps to "the deploy output says `world_behavior_packs.json: N pack(s)`".

## 2. API facts to pin (as of Bedrock 1.26.40, released 2026-08-04)

- **Stable `@minecraft/server` = 2.9.0.** npm dist-tag `latest` is 2.9.0; `beta` is 2.12.0-beta (1.26.60 preview). Learn's [1.26.40 notes](https://learn.microsoft.com/en-us/minecraft/creator/documents/update1.26.40) confirm "ships @minecraft/server v2.9.0, beta v2.10.0". Timeline: 2.0.0 stable in 1.21.90 (June 2025), 2.7.0 in 26.20 (May 2026). Stable track needs no "Beta APIs" experiment. Per the versioning page, declaring `2.9.0` is satisfied by any later 2.x. This repo's example pack already pins 2.9.0.
- **Manifest shape** ([reference](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/addonsreference/packmanifest)): `format_version: 2` with array versions is the documented stable form; `format_version: 3` (semver strings, `metadata.authors` required) is documented as "preview since 1.21.110" though Bedrock Wiki already recommends it. Teach 2; checker should accept both. Script module: `{"type":"script","language":"javascript","uuid":…,"version":[1,0,0],"entry":"scripts/main.js"}`. Dependency: `{"module_name":"@minecraft/server","version":"2.9.0"}` — never `uuid` and `module_name` in the same entry. BP→RP link: `{"uuid":"<RP header uuid>","version":[1,0,0]}`. `min_engine_version` is required.
- **Entry point**: `entry` is BP-relative; convention `scripts/main.js`; ES module syntax `import { world, system } from "@minecraft/server"`.
- **Early execution (2.x)**: at module top level only `*.subscribe`, `system.run/runInterval/runTimeout/runJob/waitTicks` are legal; `world.sendMessage` at root throws. `world.afterEvents.worldInitialize` → **`worldLoad`**; `world.beforeEvents.worldInitialize` → **`system.beforeEvents.startup`**. Any Learn/YouTube sample using `worldInitialize`, `runCommandAsync` (removed), or `entity.isValid()` (now a property) is 1.x.
- **`world.afterEvents.playerSpawn`** → `{player, initialSpawn}`; the right "hello" event for a kid because it fires when *they* appear, not at some tick. `playerJoin` fires earlier, before the player entity is usable.
- **`world.afterEvents.itemUse`** → `{itemStack, source: Player}`; filter on `itemStack.typeId === "kid:wand"`.
- **`system.runInterval(cb, ticks)`** returns an id for `clearRun`; 20 ticks = 1 s.
- **`world.sendMessage(msg)`** to everyone; **`player.sendMessage(msg)`** to one; `player.name` for greetings. `player.onScreenDisplay.setTitle/setActionBar` for flashier payoffs.
- **Scoreboard via script**: `world.scoreboard.getObjective(id) ?? world.scoreboard.addObjective(id, displayName)`; `obj.addScore(player, 1)`, `obj.getScore(player)`, `world.scoreboard.setObjectiveAtDisplaySlot(DisplaySlotId.Sidebar, {objective})`. Not callable in before-event/restricted mode.
- **`/scriptevent <messageId> <message>`** (cheats on, Game Directors) → `system.afterEvents.scriptEventReceive` → `{id, message, sourceEntity?, sourceBlock?, initiator?, sourceType}`. `system.sendScriptEvent` throws `NamespaceNameError`, so ids must be `namespace:name`. Also works from NPC dialogue buttons — the bridge to a quest.
- **Dynamic properties**: `world|entity|itemStack.getDynamicProperty(id)` / `setDynamicProperty(id, value)` with `boolean|number|string|Vector3`; `undefined` deletes; no registration step (the old `propertyRegistry` is gone); strings ≤ 32,767 bytes; stored against the **BP header UUID** — regenerating the UUID orphans saved data.
- **Logging**: `console.warn` appears in GUI and log; `console.log` is file-only on client and dropped on BDS (this repo's CLAUDE.md).

Static-check implementation note: JSON via `json.loads` after stripping `//` comments (Mojang's own files are JSONC but the learner's must not be — fail loudly on comments in learner files); JS via `node --check` plus a tiny AST walk (acorn) or, if you want zero deps, regex on normalised source. `npx mct validate` can be a second, slower gate.

## 4. Pitfalls the checker should catch before the game does

1. **Identifier drift across files** — `items/wand.json` identifier vs `item_texture.json` key vs lang key vs the string literal in `main.js`. Nothing errors; the item just has a purple-black texture or a raw name. Cross-file equality check.
2. **Wrong dependency version / mixed keys** — `"version":"1.5.0"` (Learn's own tutorial) silently runs the script in 1.x semantics where `worldLoad` does not exist; `uuid` and `module_name` in one entry breaks the pack. Also a `-beta` version needs the Beta APIs experiment, which BDS worlds won't have.
3. **Top-level world access** — `world.sendMessage` at module root throws in 2.x early execution and the whole script fails to load; only `subscribe`/`run*` allowed there.
4. **`console.log`** — file-only on client, dropped on BDS. Lint it to `console.warn`.
5. **UUID reuse** — copying a manifest keeps its UUIDs; `install-packs.py` already fails the deploy on duplicates, but the checker should say *which* file. Also warn when the BP header UUID changes after lesson 14 (dynamic properties are keyed to it).
6. **`min_engine_version` too low** — a block without `minecraft:geometry` loads under old versions and fails under ≥1.21.80; items with empty `components` fail to register under `format_version ≥ 1.26.30`. Pin `min_engine_version` and per-file `format_version` in templates and check them.
7. **Pack not listed in `world_behavior_packs.json`** — on this server that is `activate()`; the checker can read `state/deploy.json`/deploy output rather than the game.
8. **JSONC** — the learner will copy comments from vanilla files; reject `//` and `/* */` in learner JSON.
9. **BOM / wrong extension / `manifest.json.txt`** — mctools has a `nobom` rule; check first bytes and exact filenames.
10. **`before` vs `after` events** — `beforeEvents` run read-only; a scoreboard or `sendMessage` call inside one throws. Course only teaches `afterEvents`; flag any `beforeEvents` use.
11. **Case-sensitive paths** — BDS is Linux; `Scripts/Main.js` works on the kid's Mac and not on the server. Check `entry` and texture paths with exact-case existence.
12. **`/reload` leaks subscriptions** — `RELOAD_MODE=reload` means lesson 8's interval runs twice after a reload. Use restart mode for the course, or teach it as a "ghost" bug later.

**Unverified**: the lang key form `item.<ns>:<name>` for custom items comes from Bedrock Wiki's summary rather than a quoted line (Learn uses the `minecraft:display_name` component instead — either is fine); whether `format_version: 3` manifests are accepted by release 1.26.40 BDS (Learn says preview, Wiki says use it) — stay on 2 until tested on the server.
